Every Tick user belongs to an **organization**. Registering creates a personal org with you as its **owner**; clients, projects, tasks, tags and entries all live inside the org, so everything in this guide is shared with the people you invite.

## Roles

| Role | Can do |
| --- | --- |
| `owner` | Everything: rename the org, manage members and roles, create and revoke invites — including inviting and managing other **owners**. The **last owner can never be demoted or removed** (the API refuses with a 409). |
| `admin` | The same day-to-day powers, with one boundary: admins cannot touch owner accounts, and cannot grant the owner role. Attempts get a 403. |
| `member` | Track time and use the catalog; no member/org management. |

Roles are enforced on the server, and the caller's role is re-read from the database on every request — demote or remove someone and it takes effect on their very next click, not at their next login.

## Members & roles

**Settings → Members & roles** lists everyone in the org with name, email, role and rate. Owners and admins can:

- Change a member's **role** (within the boundary above).
- Set a per-member **rate override** (see below).
- **Remove** a member from the org. Their time entries stay — removal drops the membership, not the history.

### Rates per member

Each membership can carry its own $/h rate. It slots into the [Rule 2 inheritance chain](/guide/projects-clients-tasks#rule-2-rate-inheritance) between client rate and the user's personal default:

```
entry override → project → client → org member → user default
```

So a team can price one person differently across the whole org without touching any project, and each user still has a personal default (**Settings → Profile**) as the final fallback.

## Invites

**Invite member** takes an email and a role and creates an invite that is valid for **7 days** and works **once**.

1. An owner or admin creates the invite. Only owners may pick the `owner` role; inviting an address that is already a member is refused with a 409.
2. If [SMTP is configured](/installation#email-smtp), the invitee gets an email with the join link and the dialog says so. If not, the dialog shows the `…/register?invite=TOKEN` link with a **copy** button — send it however you like.
3. The register page looks the token up, prefills the email, and shows which org and role the invite is for. Registering with the token joins the existing org with the invite's role instead of creating a personal one.

Pending invites — unaccepted and unexpired — are listed with an "expires in *n*d" label, a copy-link action and **Revoke**. Revoking asks for confirmation first, because it kills a live signup link; afterwards the link returns a clear "expired or already used" message. Used and expired invites drop off the list on their own.

::note
Who can sign up *without* an invite is an operator setting: `NUXT_PUBLIC_REGISTRATION` is `open` by default, and should be `invite` or `closed` on anything exposed to the internet. See [registration modes](/installation#registration-modes).
::

## Passwords

### Changing your own

**Settings → Profile** has the password form: current password, then the new one (8 characters minimum). A wrong current password gets a deliberately vague 403.

A successful change **logs out your other sessions** and keeps the one you are using. That is the intended way to kick a stolen or forgotten device out of a workspace.

### Forgotten passwords

The login page links to **Forgot password**, which is a three-step flow:

1. You submit an email address. The reply is always the same *"Check your email — if an account exists for that address, a reset link is on its way"* — Tick will not tell a stranger whether an account exists.
2. If the address does match a user, a single-use token valid for **one hour** is created and a reset link is emailed. With no SMTP configured, the link is written to the **server console** instead (`docker compose logs app`) so a self-hoster can still recover an account.
3. The link opens `/reset-password?token=…`, where you set a new password. Used, expired and unknown tokens all get the same "invalid or expired — request a new one" page.

Finishing a reset invalidates **every** session for that user, and voids any other reset links they had outstanding.

::warning
With no SMTP set up, reset links appear in your server logs — so log access is effectively account access. Configure [SMTP](/installation#email-smtp) on any instance with more than one user.
::

::note
Tick has no email verification: an address is whatever the user typed, confirmed only by the fact that an invite or reset link reached it. The full inventory of what the app does and does not protect is on the [Security](/reference/security) page.
::
