Tick is a single Nuxt server plus a PostgreSQL database. Pick whichever of the three setups fits your host.

## Docker Compose (recommended)

The repo's `docker-compose.yml` runs the app together with a bundled **Postgres 17** (persistent named volume `tick-pgdata`). Compose reads `.env` automatically; `NUXT_SESSION_PASSWORD` is required and the stack refuses to start without it.

```bash
git clone <this-repo> tick && cd tick
cp .env.example .env
# edit .env: set NUXT_SESSION_PASSWORD (openssl rand -base64 36)
docker compose up -d
```

Open `http://localhost:3000` and register your first account.

Notes on the compose file:

- The app image defaults to `ghcr.io/OWNER/tick:latest` with a `build: .` fallback, so `docker compose up` also works from a fresh clone without a registry.
- `TICK_PORT` changes the published host port, `POSTGRES_PASSWORD` the bundled database password (both optional, see the [env table](#environment-variables)).
- Postgres is not exposed to the host by default; uncomment the `ports` block in the `db` service if you want to reach it directly.
- Both services have healthchecks; the app waits for the database to be healthy before starting.

## docker run (bring your own Postgres)

If you already run Postgres elsewhere, the image alone is enough:

```bash
docker run -d --name tick -p 3000:3000 \
  -e NUXT_DATABASE_URL='postgresql://tick:password@db-host:5432/tick' \
  -e NUXT_SESSION_PASSWORD="$(openssl rand -base64 36)" \
  ghcr.io/OWNER/tick:latest
```

::warning
Generate `NUXT_SESSION_PASSWORD` once and keep it stable — it encrypts session cookies, and changing it logs every user out.
::

Images are published to GHCR by CI on pushes to `main` (`latest`, `sha-…` tags) and on `v*` tags (semver). The image runs as a non-root user and ships a healthcheck against `/login`.

## Native (Node + PM2)

Requires **Node 22+** and a reachable Postgres.

```bash
npm ci
npm run build
export NUXT_DATABASE_URL='postgresql://tick:password@localhost:5432/tick'
export NUXT_SESSION_PASSWORD="$(openssl rand -base64 36)"   # keep it stable across restarts
node .output/server/index.mjs        # or:
pm2 start ecosystem.config.cjs       # see the file for env docs
```

PM2 inherits your shell environment; for a persistent setup put the `NUXT_*` variables in your service manager's env file (or a PM2 ecosystem `env` block) rather than exporting them ad hoc.

## Reverse proxy

The production server speaks plain HTTP on port 3000. For anything beyond localhost, put a reverse proxy in front of it for TLS, compression and security headers. The repo ships ready-made configs in `deploy/`:

- **`deploy/nginx.conf.example`** — drop into `/etc/nginx/conf.d/tick.conf`. Contains two variants: a public host with TLS (port 80 redirects to 443; uncomment one `ssl_certificate` pair — certbot paths or your internal CA's) and a commented-out plain-HTTP variant for LAN-only boxes. Run `nginx -t` and reload.
- **`deploy/Caddyfile.example`** — public hostnames get automatic Let's Encrypt certificates with zero cert config. On an internal box, uncomment `tls internal` (Caddy's built-in CA) or use an `http://` site address.

Both configs already forward the `Host` and `X-Forwarded-*` headers Tick needs (so session cookies and client IPs work through the proxy), allow 8 MB request bodies for CSV import, disable caching on `sw.js` and `manifest.webmanifest` so installed PWAs pick up updates promptly, enable gzip, and set sane security headers. Details and setup commands: `deploy/README.md`.

::warning
If you enable the (commented) HSTS header, do it only once TLS is known-good — browsers cache it, and a broken certificate then locks users out for the whole max-age.
::

## Automatic migrations

The built server applies pending SQL migrations from `server/db/migrations` on startup — a Nitro plugin runs them before the first request, in Docker and native installs alike. That means upgrades are just "pull new version, restart".

To run migrations out-of-band instead (e.g. in a CI step or with a locked-down DB user), set `NUXT_AUTO_MIGRATE=false` and apply them yourself with `npx drizzle-kit migrate`.

## Environment variables

| Variable | Required | Default | Description |
| --- | --- | --- | --- |
| `NUXT_DATABASE_URL` | yes | — | Postgres connection string, e.g. `postgresql://tick:password@localhost:5432/tick` |
| `NUXT_SESSION_PASSWORD` | yes | — | Session cookie encryption secret, 32+ chars. Generate: `openssl rand -base64 36`. Changing it logs everyone out |
| `NUXT_AUTO_MIGRATE` | no | `true` | Apply pending SQL migrations on production startup; `false` to run them out-of-band (`npx drizzle-kit migrate`) |
| `NUXT_MIGRATIONS_DIR` | no | `<cwd>/server/db/migrations` | Override the migrations folder location |
| `NITRO_HOST` | no | `0.0.0.0` (image) | Bind address of the production server |
| `NITRO_PORT` | no | `3000` | Port of the production server |
| `POSTGRES_PASSWORD` | no | `tick` | docker-compose only: password for the bundled Postgres |
| `TICK_PORT` | no | `3000` | docker-compose only: host port the app is published on |

## Development setup

```bash
npm i
cp .env.example .env      # point NUXT_DATABASE_URL at a local Postgres
npm run db:push           # create the schema (dev uses push, not migrations)
npm run db:seed           # demo org + ~3 weeks of entries
npm run dev
```

Seed credentials: **mara@example.com** / **tick-demo** (org "Hollow Studio"). Other scripts: `npm run typecheck`, `npm run db:generate` (writes a new SQL migration from schema changes — commit the `server/db/migrations` output so deployed instances pick it up).
