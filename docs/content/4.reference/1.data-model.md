One PostgreSQL database, managed by Drizzle ORM. Migrations live in `server/db/migrations` and [apply automatically](/installation#automatic-migrations) on startup.

## Entities

| Table | Columns (essentials) |
| --- | --- |
| `users` | `id`, `name`, `email` (unique), `password_hash` (scrypt, `salt:hex`), `default_rate` ($/h), `theme` (jsonb), `session_version` (int, revocation stamp) |
| `orgs` | `id`, `name` |
| `org_members` | `org_id` + `user_id` (PK), `role` (`owner` \| `admin` \| `member`), `rate` (per-member override) |
| `clients` | `id`, `org_id`, `name`, `rate?`, `deleted_at?` |
| `projects` | `id`, `org_id`, `name`, `client_id?`, `rate?`, `billable_default`, `estimate_minutes?`, `visibility` (`private` \| `public`), `archived`, `deleted_at?` |
| `tasks` | `id`, `org_id`, `name`, `project_id?`, `estimate_minutes?`, `done`, `deleted_at?` |
| `tags` | `id`, `org_id`, `name` (lowercase, unique per org), `deleted_at?` |
| `time_entries` | `id`, `org_id`, `user_id`, `name`, `ref_type` (`client` \| `project` \| `task` \| null), `ref_id?`, `billable`, `rate_override?`, `start`, `end?`, `deleted_at?` |
| `entry_tags` | `entry_id` + `tag_id` (PK) |
| `invites` | `id`, `org_id`, `email`, `role` (`owner` \| `admin` \| `member`), `token` (unique), `expires_at`, `accepted_at?` |
| `password_reset_tokens` | `id`, `user_id`, `token` (unique), `expires_at`, `used_at?` |

All timestamps are `timestamptz`. Note what is *absent*: tasks have no rate (rates come from the project chain), and entries have no `project_id`/`client_id` columns — that's Rule 1.

`role` on `org_members` and `invites`, `visibility` on `projects` and `ref_type` on `time_entries` are text columns with `CHECK` constraints rather than enums, so the allowed values live in one place and migrate cheaply.

## Sessions and revocation

Sessions are sealed cookies — there is no session table. `users.session_version` is what makes revocation possible: the version is stamped into the cookie at login, every authenticated request compares the stamp against the live column, and a password **reset** or **change** increments it. Cookies carrying an older stamp are cleared and answered `401` on their next request. A password change re-stamps the calling session so only *other* devices are logged out; a reset logs out everything. See [Security](/reference/security#sessions).

`password_reset_tokens` rows are single-use and live one hour. Finishing a reset marks the used token *and* every other outstanding token for that user as used, so an older link in an inbox cannot be replayed.

## The running timer

The timer is not a separate concept: it is a `time_entries` row with `end IS NULL`. A **partial unique index** (`user_id` where `end is null and deleted_at is null`) guarantees at most one running entry per user at the database level — a second `start` gets HTTP 409.

## The rules

**Rule 1 — deepest reference only.** An entry stores one of `client | project | task | nothing` in `ref_type`/`ref_id`. Project and client are derived at read time (`task → project → client`), never copied. Re-parenting a task re-files its history.

**Rule 2 — rate inheritance, first non-null wins.**
`entry.rate_override → project.rate → client.rate → org_member.rate → user.default_rate`.
`billable` defaults from `project.billable_default` when a project resolves, else `true`. `amount = hours × rate`, only when billable. Resolution happens server-side; DTOs carry `resolvedRate`, `rateOverridden` and (for projects) `rateSource`.

**Rule 3 — cascade delete.** Client/project deletion cascades downward via explicit checkboxes (Projects ⇒ Tasks ⇒ Entries). Unchecked survivors are *detached*, not deleted: projects lose `client_id`, tasks lose `project_id`, entries pointing at a deleted object get `ref_type = null`. Time is never lost silently.

**Rule 4 — soft deletion.** Every delete sets `deleted_at` and lands in the 30-day trash; hard-purge happens automatically after 30 days (on the next trash load) or explicitly via *Delete forever*. Deleting a tag only strips labels (`entry_tags` rows), never time. Every delete API returns a `DeleteResult` snapshot (`deleted` ids per entity + `detached` counts) that `POST /api/restore` can undo exactly; cascade deletes return a `CascadeDeleteResult`, which adds a `relinked` snapshot of the references they cleared so undo can put them back. The undo window itself is a per-browser preference — 8 seconds by default, 3–30 in **Settings → Profile**.

## DTOs

API responses use shared DTO shapes (see `shared/types/`): `EntryDto` (with resolved `ref` chain, `resolvedRate`, `durationSec`, `amount`, `tags`), `ClientDto` / `ProjectDto` / `TaskDto` / `TagDto` (with usage counts and tracked totals), `TimerState`, `DashboardSummary`, `ReportSummary`, `ImportPreview` / `ImportCommitResult`, the settings DTOs (`OrgInfoDto`, `OrgMemberDto`, `InviteDto`, `InviteLookupDto`, `TrashDto`) and the mail DTOs (`InviteCreateDto` with its `token` + `emailSent`, `ForgotResponseDto`, `ResetResponseDto`). Clients never compute chains or rates — the server resolves everything.
