Tick is a small self-hosted app, not a managed service. This page is the honest inventory: what the code does, and what it leaves to you. Nothing here claims an audit.

## What the app does

### Passwords

- Hashed with Node's **scrypt** (`node:crypto`), one random salt per user, stored as `salt:hex`. No plaintext, no reversible encryption, no third-party service.
- Minimum 8 characters, enforced on register, reset and change. There is no complexity rule and no breach-list check.
- Login answers a single generic `401` for both a wrong email and a wrong password, and verifies against a dummy hash when the email is unknown so response time does not reveal whether an account exists.

### Sessions

- Sessions are **sealed, signed cookies** (nuxt-auth-utils), encrypted with `NUXT_SESSION_PASSWORD`. There is no session table, so there is nothing for an attacker to read server-side — and nothing to revoke individually.
- Authorization is never trusted from the cookie. Every authenticated request re-reads the caller's org membership and role from the database: a removed member is locked out on the next request, a demoted one loses privileges immediately.
- Revocation works through `users.session_version`: a password **reset** invalidates every session, a password **change** invalidates every *other* session and keeps the current one. Those are the only ways to kill a live session short of rotating `NUXT_SESSION_PASSWORD` (which logs out everybody).

### Tenancy

- Every query is scoped by `org_id`, and entry mutations additionally by `user_id`. Ids are UUIDs and validated as such, so a guessed id from another org returns `404`, not data.
- Role gates live on the server, not just in the UI: only owners and admins can rename the org, manage members or manage invites; only owners can create or grant the `owner` role or manage other owners; the last owner cannot be demoted or removed.

### Public endpoints

- `POST /api/auth/{login,register,forgot,reset}` and `GET /api/invites/lookup/:token` are the only routes reachable without a session.
- `POST /api/auth/forgot` always answers the same `{ok: true}` and pads its response time, so it cannot be used to enumerate accounts. Reset tokens are 36 random bytes, single-use, and expire after one hour.
- Validation errors on those routes are deliberately terse — `{statusMessage: 'Invalid input', data: {fields: […]}}`, field names only — so schema internals never leak.

### Rate limiting

`POST` to each auth endpoint is limited to **10 requests per IP per minute** by default; over the limit the server answers `429` with a `Retry-After` header. Set [`NUXT_AUTH_RATE_LIMIT`](/reference/env#variables) to change the ceiling, or `0` to disable it and let a proxy do the job.

::note
The window is in-memory and keyed on the socket address — not `X-Forwarded-For`, which a client can forge when the app is exposed directly. Behind a reverse proxy every request appears to come from the proxy, so the limit becomes effectively instance-wide. Multi-node deployments should rate-limit at the proxy and set `NUXT_AUTH_RATE_LIMIT=0`.
::

### Response headers

Middleware sets these on every response — pages, assets and API alike:

| Header | Value |
| --- | --- |
| `Content-Security-Policy` | `default-src 'self'`, no external script hosts (only `fonts.googleapis.com` / `fonts.gstatic.com` for fonts), `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `frame-ancestors 'none'` |
| `X-Frame-Options` | `DENY` |
| `X-Content-Type-Options` | `nosniff` |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |

`x-powered-by` is stripped. `script-src` does include `'unsafe-inline'` — Nuxt's inline hydration payload requires it — so the CSP is a defense in depth, not a hermetic seal. **HSTS is not set by the app**: it belongs at the TLS-terminating proxy, and both shipped [proxy configs](/installation#reverse-proxy) carry it commented out.

### Input and payload limits

- API request bodies are capped at **1 MB** (`413`); a mutation without a `Content-Length` is refused with `411` so a chunked body cannot slip past the check. `/api/import/*` has its own **5 MB** cap.
- Every body, query and route param goes through zod. `users.theme` accepts known keys only and is capped at 2 KB — a jsonb column is not a dumping ground.
- CSV export escapes per RFC 4180 **and** neutralizes spreadsheet formula injection: a text field starting with `=`, `+`, `-`, `@`, tab or CR is prefixed with an apostrophe, so a maliciously named entry cannot execute in Excel or Sheets.

## What you have to do

::warning
Tick speaks plain HTTP and assumes something in front of it. The list below is not optional for anything reachable beyond localhost.
::

1. **Terminate TLS at a reverse proxy.** Use the shipped [`deploy/nginx.conf.example` or `deploy/Caddyfile.example`](/installation#reverse-proxy). Session cookies protect nothing over plain HTTP on an untrusted network.
2. **Add HSTS at the proxy** — but only once the certificate is known-good. Browsers cache it, and a broken cert then locks users out for the whole `max-age`.
3. **Generate a strong `NUXT_SESSION_PASSWORD`** (`openssl rand -base64 36`), keep it out of version control, and keep it stable. It is the key to every session cookie.
4. **Pick a [registration mode](/installation#registration-modes).** The default is `open` — anyone who can reach the host can create a workspace. Public instances should run `invite` or `closed`.
5. **Restrict the database.** Postgres is not exposed to the host by the shipped Compose file; keep it that way, and give the app its own role rather than a superuser. With `NUXT_AUTO_MIGRATE=false` the runtime user needs no DDL rights at all.
6. **Back up Postgres.** The 30-day trash is an undo affordance, not a backup — *Delete forever*, a purge past retention and a dropped volume are all unrecoverable. `pg_dump` on a schedule, restore-tested.
7. **Watch the logs** if you run without SMTP: password-reset links are printed to the server console there, which means anyone who can read your logs can take over an account.
8. **Never run [demo mode](/reference/env#variables) against real data.** It wipes and reseeds the demo org on boot.

## Known gaps

Stated plainly, so nobody is surprised:

- **No email verification.** A registered address is never confirmed.
- **No two-factor auth**, no SSO, no OIDC.
- **No per-session revocation.** You can log out everywhere (password change or reset), not a single device.
- **No audit log.** Who deleted what is not recorded beyond the trash's `deleted_at`.
- **No field-level encryption.** Everything is readable by anyone with database access.
- **Rate limiting is single-node and in-memory** — see the note above.
